# 任务契约

任务契约用于把用户需求、范围边界、成功标准和验证方式写成可交接的结构化事实。它解决的问题不是“多写计划”，而是避免 Agent 在实现后改写目标、遗漏验收点或把未验证内容当成完成。

## 使用时机

以下任务必须先建立契约：

- 跨文件、跨模块、跨路由、跨状态或跨工具链。
- 涉及运行时交互、地图/canvas、数据生成链路或公开接口。
- 需要超过一次实现-验证循环。
- 用户要求长期执行、分阶段交付或后续 Agent 接手。

简单文案、单文件静态文档或无运行时影响的小改动，可以只在回复中说明目标和验证方式，不必创建契约文件。

## 契约位置

- 通用模板：复制 `core/templates/task-contract.json` 作为起点。
- 项目任务：优先写入 `.agents/project/memory/current/contract.json`。
- 长任务或多轮任务：可按项目约定写入 `.agents/project/runs/<task-id>/contract.json`，并在 `current/progress.md` 中链接。

## 写入规则

- 成功标准必须可判定，避免“体验更好”“尽量优化”这类不可验证描述。
- `scope.in` 写本次必须做的内容，`scope.out` 写明确不做的内容。
- 每个 `success_criteria` 必须有验证方法或人工边界。
- 契约变更必须记录在 `change_log`，不能在实现后静默改目标。
- 验证失败时，只更新 `status` 和 `evidence`，不要删除失败标准。

## 生命周期

1. Agent 根据用户需求和任务路由创建契约草案。
2. 如存在产品、权限或高风险边界不清，先问用户；否则按保守假设继续。
3. Generator 按契约实现最小可行改动。
4. Evaluator 按契约逐项验证，并输出评估报告。
5. 未达标时回到实现阶段；达标后压缩契约和证据到最终回复或当前记忆。

## 通过条件

契约通过需要同时满足：

- `success_criteria` 中所有 `required: true` 项均有证据支持。
- 未验证项已标注原因、风险和人工确认边界。
- 实现没有扩大到 `scope.out`。
- Evaluator 报告结论为 `pass`，或明确列出用户接受的剩余风险。
